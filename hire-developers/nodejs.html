Where Node Earns Its Keep

Six use-cases our Node bench excels at.

The shapes of work Node.js is genuinely well-suited for — and where our experts have shipped the most.

REST APIs

OpenAPI-first design, JSON Schema validation, versioned endpoints, pagination that scales beyond offset, and idempotency keys for write operations.

GraphQL gateways

Federation with Apollo Router, schema stitching for legacy backends, DataLoader for the n+1 problem, persisted queries for client safety.

WebSocket & real-time

Presence, collaborative editing, live dashboards. Socket.io for portability, native ws or uWebSockets when performance matters, with sticky sessions handled at the load balancer.

BFFs (Backends-for-Frontend)

A thin Node layer between your client and your downstream services — auth, aggregation, response shaping. Especially valuable when you have a mobile app and a web app to feed.

Microservices

Service boundaries that reflect domain ownership, not org chart. Async messaging with Kafka or NATS, contract testing with Pact, distributed tracing as table stakes.

AI agent backends

Streaming LLM responses over SSE, tool-calling orchestration, long-running agent runs with durable execution via Temporal. The infra layer behind every serious agent in production.

Runtime & Framework

Five runtimes, with informed opinions.

We have shipped on all of these. Here is when each makes sense — and when it does not.

Express

Boring, dependable, every Node developer can read it. Default for small services where the framework should disappear.

Nest.js

Our default for new services larger than a single file. Dependency injection, modules, decorators — discipline you do not have to invent.

Fastify

When the use-case demands raw throughput. Schema-driven validation, JSON serialization that runs faster than Express by a meaningful margin.

Hono

For edge runtimes — Cloudflare Workers, Vercel Edge, Deno Deploy. The right shape when the workload moves close to the user.

Bun

Used selectively. The DX is excellent and the cold starts are real. We will tell you honestly whether your project is one Bun should run in production yet.

Discipline

Four habits that separate a senior Node developer.

The practices we hire for and reinforce on every engagement.

Clustering & PM2

One Node process per CPU core, with PM2 or the native cluster module. Sticky sessions for WebSockets, zero-downtime reloads, memory-limit auto-restart.

Event-loop hygiene

Blocking work into worker threads, sync I/O caught in code review, lag monitoring with `perf_hooks.monitorEventLoopDelay` exported to Prometheus.

Observability by default

OpenTelemetry traces wired from day one, structured logging with pino, RED metrics on every endpoint, alerting that knows the difference between a deploy spike and a real incident.

Load-test thresholds

k6 or artillery against staging before features ship. Documented latency SLOs at p50, p95, p99. The number is in the README, not in someone's head.

We've Seen This Go Wrong

Anti-patterns we refactor out, quietly.

Common Node mistakes we have inherited from prior teams, fixed, and stopped seeing in code review. Not a roast — a list of things to look for in your own code.

If any of these show up in your codebase, it does not mean someone made a bad call. It usually means a junior expert made the most reasonable call they could with the context they had. The senior bar is recognizing the shape early.

  • Synchronous file reads on the hot path — `readFileSync` inside a request handler, blocking the loop for everyone
  • Unbounded promise concurrency — `Promise.all` over a thousand DB queries with no `p-limit`, starving the pool
  • Logging objects with circular references — JSON.stringify blowing up the process at the worst possible moment
  • Express middleware that swallows errors — `try { } catch { res.status(500).end() }` with no log and no trace
  • `new Date()` arithmetic across timezones — math that worked on the dev machine and broke for clients abroad
  • Singleton state in a clustered process — counters and caches that work in dev with one process and lie in prod with eight
  • Streaming responses without backpressure — the server happily filling memory because the client is reading slowly
  • Cron jobs in the same process as the API — your scheduled report quietly killing your p99 every hour on the hour

Node FAQ

Three questions Node buyers ask first.

JavaScript or TypeScript — and how strict?
TypeScript by default, in `strict` mode, with `noUncheckedIndexedAccess` on for new services. For existing JavaScript codebases, we will not force a migration — but we will write any new files in TypeScript and incrementally convert hot files when they change anyway. The cost-of-bugs delta is large enough that we treat this as non-negotiable for greenfield work.
Should we use Nest.js or stay with Express?
Nest.js for any service that will outlive a single quarter and have more than two experts touching it. Express for small, single-purpose services where the framework's invisibility is a feature. Fastify when the routing layer is on the hot path of your latency budget. We will recommend on a case-by-case basis — our experts are fluent in all three.
Can your Node developers work on a Java or Python backend codebase too?
A subset of our Node bench is comfortable reading Java or Python, and most can debug their way through one. But for sustained work in another language we would suggest a hire from the matching bench — paying for context-switching dressed up as a Node engagement does not serve you. Tell us the scope; we will give you the right answer, even if it points away from Node.

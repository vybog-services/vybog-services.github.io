App Router vs. Pages Router

An opinionated comparison — written by people shipping both.

The Next.js community is still divided on this. Here is the version that reflects what we actually recommend to clients on engagement after engagement.

Dimension App Router Pages Router
Default for new projects Yes, since Next 13.4 Only when team familiarity dictates
Data fetching model RSC + server actions — direct DB access in components getServerSideProps / getStaticProps — explicit boundary
Bundle-size pressure Lower — server components ship zero JS Higher — every page hydrates fully
Mental model cost Higher — RSC, Suspense, server/client boundary Lower — familiar React mental model
Ecosystem maturity Most major libs now RSC-aware, some still adapt Stable, everything works, no surprises
Migration approach Incremental — route-by-route, both can coexist Stay on it if migration ROI is unclear

Short version: new project, App Router. Existing Pages Router app that ships, stay — until a feature is genuinely easier in the App Router.

Edge runtime

Middleware patterns

Auth-gated route segments, tenant resolution from subdomain, feature flag routing, rate limiting at the edge, custom headers for downstream services.

Editorial

The SEO case for Next.js — without the hype.

A single-page app feels fast to the developer who built it. It does not feel fast to the search crawler, the social-card scraper, the slow phone on a hotel WiFi, or the user who lost JavaScript a minute ago.

Next.js earned its position in the market by collapsing that whole conversation: server-rendered HTML out of the box, with progressive enhancement, with the same React you already write. Pages that look fully rendered to the crawler, that show meaningful content before JavaScript boots, that let Open Graph cards work without a separate static-site generator.

For content-driven products — SaaS marketing sites, documentation portals, e-commerce storefronts, customer help centers, B2B landing pages, anything where organic search is a meaningful channel — Next.js is the most defensible technical choice in the React ecosystem in 2026. The performance budget is set up correctly by default and the SEO surface area is not an afterthought added in week ten.

Deployment

Three places we deploy Next.js — with honest trade-offs.

Easiest

Vercel

The path of least resistance. Edge functions, image optimization, ISR, observability — all wired in. Best for product teams who do not want to think about infrastructure.

Watch-out: bandwidth and function-invocation cost at scale.

Most flexible

Self-hosted Node

Standalone build mode, Node 20 LTS behind a reverse proxy, your own ISR cache, your own CDN in front. Works on any cloud and on bare metal.

Watch-out: you own the edge function story yourself.

Modern

Containerized

Docker image deployed to Kubernetes, Cloud Run, ECS, or Fly.io. Reproducible builds, multi-region deploys, autoscaling, integrates with your existing platform team.

Watch-out: cold starts matter — size and warm-up matter.

Next.js FAQ

Three questions Next.js buyers ask.

We are stuck on Pages Router. Is it worth migrating to App Router?
Usually not as a single big project. The App Router and Pages Router can coexist in the same Next.js app, route by route, indefinitely. We typically migrate the high-value routes that benefit from RSC (data-heavy dashboards, SEO-critical pages) and leave the rest until they need to change anyway. A "full migration" project usually does not justify itself on a P&L.
Vercel or self-hosted — what do you recommend?
Vercel until your bandwidth or function-invocation bill starts pinching, or until you have a security or sovereignty requirement that Vercel does not satisfy. After that, self-hosted on Cloud Run, ECS, or Fly.io with a managed Postgres and a Redis cache. We have moved several clients off Vercel and the math is usually clearer than people expect.
Do we still need a separate backend, or can server actions replace it?
Server actions cover a lot — they remove the need for a thin API layer between your client and your database for the common CRUD case. But you will still want a real backend for: any operation that needs to outlive the request, anything that other consumers (mobile apps, partners, internal services) need to call, and anything regulated or audited. We will help you draw that line on the architecture call.
